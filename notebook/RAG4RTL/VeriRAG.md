VeriRAG: A Retrieval-Augmented Framework for Automated RTL Testability Repair

https://arxiv.org/pdf/2507.15664

这是一篇关于 **VeriRAG**（A Retrieval-Augmented Framework for Automated RTL Testability Repair）的详细介绍。

这篇论文由 **香港中文大学 (CUHK)**、**加州大学圣地亚哥分校 (UCSD)** 和 **香港大学 (HKU)** 的研究团队共同完成，发表于 2026 年 1 月。论文提出了一种基于检索增强生成（RAG）的框架，专门用于解决电子设计自动化（EDA）领域中的**可测性设计（DFT）**问题。

以下是该论文的详细解读：

### 1. 核心背景与痛点
*   **领域**：计算机辅助设计（CAD）与硬件设计自动化（EDA）。
*   **问题**：虽然大语言模型（LLM）在代码生成和调试方面表现出色，但在**可测性设计（DFT）**领域仍处于探索初期。DFT 旨在确保芯片在制造后能够被有效测试（例如扫描链插入、时钟复位处理）。如果在 RTL（寄存器传输级）阶段没有处理好 DFT 问题，后续的物理实现和自动测试模式生成（ATPG）将面临巨大困难，且修复成本极高。
*   **挑战**：现有的 LLM 往往缺乏特定的硬件 DFT 领域知识，导致在修复 DFT 错误时成功率极低（Zero-shot 效果差）。

### 2. 核心贡献：VeriRAG 框架与 VeriDFT 数据集
论文提出了 **VeriRAG**，这是首个用于辅助 DFT 的 EDA 框架。其核心包含两部分：

*   **VeriDFT 数据集**：
    *   这是一个基于 Verilog 的 DFT 数据集，专门用于训练和检索。
    *   **构建过程**：基于开源数据集清洗而来，包含了 437 个 Verilog 文件。
    *   **内容**：涵盖了 4 种典型的 RTL 级 DFT 错误模式（ACNCPI, CLKNPI, CDFDAT, FFCKNP），并且每个错误样本都配对了经过人工验证的“修复后代码”。
*   **VeriRAG 框架**：
    *   **结构感知检索**：不仅仅是文本匹配，而是通过一个**自编码器（Autoencoder）**学习 RTL 代码的硬件结构特征（基于 JSON 表示），从而精准检索出与当前错误最相似的参考案例。
    *   **迭代修正流水线**：LLM 不是一次性生成结果，而是结合检索到的参考案例进行修改，并通过 EDA 编译器和 DFT 工具的反馈（诊断报告）进行多轮迭代，直到代码既可综合又符合 DFT 规范。

### 3. 方法论深度解析 (Methodology)

#### A. 数据集构建 (VeriDFT)
*   **清洗策略**：过滤掉了测试平台（Testbench）和不可综合的代码。
*   **错误类型**：聚焦于四种关键的 DFT 违规类型：
    1.  **ACNCPI**：异步复位不可控。
    2.  **CLKNPI**：内部生成或门控时钟。
    3.  **CDFDAT**：时钟网络被用作数据。
    4.  **FFCKNP**：触发器驱动时钟。
*   **JSON 表示**：使用 Yosys 工具将 Verilog 转换为 JSON 格式。这种格式去除了无关的变量名，保留了门级拓扑连接结构，非常适合衡量硬件结构的相似性。

#### B. 自编码器训练 (Autoencoder Training)
*   **目标**：训练一个编码器，能将 RTL 设计映射为向量，使得结构相似且具有相同 DFT 错误的电路在向量空间中距离相近。
*   **损失函数**：采用多任务学习，包含三部分：
    1.  **重构损失 (Reconstruction Loss)**：确保编码能还原原始结构。
    2.  **分类损失 (Classification Loss)**：确保编码包含 DFT 错误类型信息。
    3.  **对比损失 (Contrastive Loss)**：拉近相同错误类型样本的距离，推开不同错误类型样本的距离。

#### C. RAG 推理与迭代修复
1.  **检索**：对于待修复的代码，将其转为 JSON 并编码，计算与数据库中所有样本的余弦相似度，找出最相似的“参考-修复”对。
2.  **提示 (Prompting)**：将参考案例和修复案例放入 Prompt，指导 LLM 如何修改当前代码。
3.  **反馈循环**：修改后的代码送入 EDA 工具（Xcelium 编译器 + Conformal LEC）。
    *   如果有 DFT 错误或不可综合，报错信息会反馈给 LLM，进行下一轮修改。
    *   **终止条件**：代码可综合、无 DFT 错误、且通过逻辑等价性检查（LEC）。

### 4. 实验结果

*   **基线对比**：对比了 Zero-shot（直接问 LLM）、No RAG（只给背景知识）、Random RAG（随机给参考案例）。
*   **主要发现**：
    *   **GPT-o1 表现最佳**：在 VeriRAG 框架下，GPT-o1 的最终成功率为 **53.76%**。
    *   **巨大的提升幅度**：相比 Zero-shot 基线（6.96%），VeriRAG 实现了 **7.72 倍**的提升。
    *   **结构检索的重要性**：相比于 Random RAG，使用结构感知检索（VeriRAG）的成功率显著更高，证明了“找对参考案例”是关键。
*   **模型差异**：Grok-3 在引入 VeriRAG 后提升幅度最大（从 2.85% 提升至 40.26%），显示了不同模型利用外部知识的能力差异。

### 5. 总结

VeriRAG 证明了在高度专业化和结构化的领域（如芯片设计 DFT），**单纯的通用大模型是不够的**。通过引入**结构感知的检索（Structure-Aware Retrieval）**和**工具引导的迭代（Tool-Guided Iteration）**，可以极大地释放 LLM 在专业领域的修复潜力。

该研究不仅提供了一个有效的 DFT 修复工具，还开源了 **VeriDFT 数据集**和代码，为后续的硬件 AI 研究提供了重要的基准。

简单来说，**VeriRAG 解决的既不是纯粹的“语法错误”（Syntax Error），也不是纯粹的“功能错误”（Functional Bug），而是“可测性设计缺陷”（DFT Violations）。**

为了让你更清晰地理解这三者的区别，我结合论文内容为你详细拆解：

### 1. 语法错误 (Syntax Error)
这是最基础的错误，类似于人类写文章时的“错别字”或“语序不通”。

*   **定义**：代码不符合 Verilog/VHDL 语言的语法规则，导致无法被编译器（如 Xcelium）翻译成电路网表。
*   **例子**：忘记写 `end`，括号不匹配，或者写了一个不存在的关键字。
*   **与 VeriRAG 的关系**：
    *   **VeriRAG 不解决这个问题**。论文明确提到，它处理的代码必须是**“可综合的”（Synthesizable）**。
    *   如果输入代码有语法错误，编译器直接报错退出，根本无法进行后续的 DFT 检查。论文假设输入的代码至少在语法上是正确的，否则连电路都生成不出来。

### 2. 功能错误 (Functional Error)
这是逻辑层面的错误，类似于文章“词不达意”。

*   **定义**：代码能通过编译，生成的电路也能工作，但**行为不符合设计需求**。它做错了事。
*   **例子**：设计要求加法器，结果做成了减法器；或者状态机跳转条件写反了。
*   **与 VeriRAG 的关系**：
    *   **VeriRAG 不修复功能错误**。
    *   论文的核心约束之一是**“逻辑等价性检查（LEC）”**。VeriRAG 在修复完成后，必须通过 LEC（Logic Equivalence Check）工具验证。LEC 通过意味着：**修复后的电路逻辑功能与修复前完全一致**。
    *   **结论**：VeriRAG 只能改电路的“结构”（为了方便测试），绝对不能改电路的“行为”（功能）。如果原来的功能是错的，VeriRAG 修完后功能依然是错的（但结构更利于测试了）。

### 3. VeriRAG 解决的“DFT 错误” (Design for Testability Errors)
这是物理实现和制造层面的错误，类似于设计了一辆跑车，但没留修车的千斤顶接口。

*   **定义**：电路在功能上是完美的，但在制造出来后**无法被有效测试**。如果芯片里有瑕疵（Defect），我们修不了，也测不出来。
*   **核心痛点**：DFT 错误通常涉及时钟（Clock）、复位（Reset）和扫描链（Scan）的连接方式。如果在 RTL 阶段不处理，等到后端物理设计时再改，成本极高。
*   **论文中解决的具体 DFT 错误类型**（见论文 Section II.B）：
    1.  **ACNCPI** (Asynchronous set/Reset Not Controllable from Primary Inputs)：异步复位信号无法从芯片的主引脚控制。**后果**：测试时无法强制复位电路，导致测试失败。
    2.  **CLKNPI** (Internally Generated or Gated Clocks)：门控时钟或内部生成的时钟。**后果**：导致时钟树综合困难，或者测试时无法控制时序。
    3.  **CDFDAT** (Clock Net used as Data)：时钟网络被用作数据信号。**后果**：破坏时钟信号的完整性。
    4.  **FFCKNP** (Flip-Flop driven Clocks)：触发器驱动时钟。**后果**：产生非平衡的时钟树，导致时序违例。

### 总结对比表

为了让你一目了然，我整理了以下对比表格：

| 维度 | 语法错误 (Syntax) | 功能错误 (Functional) | DFT 错误 (VeriRAG解决的) |
| :--- | :--- | :--- | :--- |
| **通俗比喻** | 写文章有错别字 | 写文章意思写反了 | 建房子没留窗户(无法通风) |
| **能否编译** | **不能** (编译器报错) | 能 (生成电路) | 能 (生成电路) |
| **电路能否工作** | 无电路，无法工作 | 能工作，但结果不对 | **能工作，结果也对** |
| **主要后果** | 无法生成芯片 | 芯片逻辑功能错误 | **芯片造出来后无法有效测试** |
| **VeriRAG 的态度** | **不处理** (输入需语法正确) | **禁止修改** (必须通过 LEC 检查) | **专门修复** (核心目标) |

### 一句话概括
**VeriRAG 是一个“外科手术”工具：它假设你的代码（病人）没有语法发烧（Syntax），也没有逻辑疯癫（Function），但它专门给你的代码（身体）安装“测试接口”（DFT），并且保证安装完后，你的代码（人）还是原来那个人（逻辑等价）。**
